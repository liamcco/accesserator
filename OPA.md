# OPA Setup in Accesserator (Current Implementation)

This document describes the current OPA setup after the simplification:

- the discovery server serves only the discovery bundle (`/discovery.tar.gz`)
- application pods (OPA sidecars) pull the signed authz bundle directly from GHCR/OCI
- GitHub token and bundle public key are injected into the OPA sidecar as environment variables (not into the discovery pod)

## High-Level Flow

1. A namespace is labeled to enable Accesserator pod webhooks
2. A Skiperator `Application` is labeled `skiperator/security=enabled`
3. A `SecurityConfig` enables `spec.opa`
4. The `SecurityConfig` controller creates:
   - OPA config `ConfigMap`
   - OPA discovery `ConfigMap`
   - OPA discovery `Service`
   - OPA discovery `Deployment` (nginx only)
   - discovery ingress/egress `NetworkPolicy`
5. Pod webhooks inject the OPA sidecar into the app pod, plus:
   - OPA config volume
   - GitHub token env var (from `spec.opa.githubToken`)
   - bundle public key env var (from `spec.opa.bundlePublicKey`)
6. OPA starts, fetches the discovery bundle from the internal discovery service
7. The discovery bundle tells OPA to fetch the real bundle directly from OCI (`bundlePath:bundleVersion`)
8. OPA uses the injected GitHub token + public key env vars to download and verify the signed bundle

## Prerequisites

### Namespace webhook enablement

The webhook configs are namespace-scoped via label:

- `accesserator-webhooks=enabled`

### Skiperator application enablement

The Skiperator `Application` must be labeled:

- `skiperator/security=enabled`

The pod webhook resolves the app via pod label:

- `application.skiperator.no/app-name`

### `SecurityConfig` requirements for OPA

Relevant `spec.opa` fields:

- `enabled`
- `githubToken` (Secret key selector)
- `bundlePublicKey` (ConfigMap key selector)
- `bundlePath` (for example `ghcr.io/kartverket/opa-bundle`)
- `bundleVersion` (for example `latest` or `v1.2.3`)

The controller resolver combines these into:

- `<bundlePath>:<bundleVersion>`

## What the Controller Creates

For app `app` in namespace `test` (OPA enabled), Accesserator creates:

- `app-opa-config` (`ConfigMap`)
- `app-opa-discovery-config` (`ConfigMap`)
- `app-opa-discovery` (`Service`)
- `app-opa-discovery` (`Deployment`)
- `app-opa-discovery-egress` (`NetworkPolicy`)
- `app-opa-discovery-ingress` (`NetworkPolicy`)

Generated by:

- `internal/controller/securityconfig_controller.go`
- `pkg/resourcegenerators/opa/`

## OPA Config (`<app>-opa-config`)

The OPA `config.yaml` is generated into `config.yaml` in the ConfigMap.

It configures:

- `discovery-server` service:
  - internal URL: `http://<app>-opa-discovery.<ns>.svc.cluster.local`
- `oci-registry` service (`type: oci`):
  - URL derived from the bundle ref host (for example `https://ghcr.io`)
  - bearer token read from env var:
    - `${GITHUB_TOKEN}`
- `keys.bundle-signing` metadata:
  - algorithm `RS256`
  - key read from env var:
    - `${OPA_PUBLIC_KEY}`
- discovery:
  - service `discovery-server`
  - resource `/discovery.tar.gz`
  - polling 10-30s

Important detail:

- The generated OPA config references env vars, so the webhook injects:
  - `GITHUB_TOKEN` from `spec.opa.githubToken`
  - `OPA_PUBLIC_KEY` from `spec.opa.bundlePublicKey`

## Discovery Config (`<app>-opa-discovery-config`)

The discovery ConfigMap contains:

- `default.conf` (nginx config)
- `discovery.tar.gz` (OPA discovery bundle archive)

The discovery bundle (`tar.gz`) contains `data.json` with a bundle entry for `authz` that now points directly to OCI:

- service: `oci-registry`
- resource: `<bundlePath>:<bundleVersion>` (full OCI ref)
- signing key id: `bundle-signing`
- polling: 10-30s

This means the discovery server no longer hosts `/bundles/authz.tar.gz`.

## Discovery Service + Deployment (`<app>-opa-discovery`)

### Service

- ClusterIP service exposing nginx on port `80` -> container port `8080`

### Deployment (simplified)

The discovery deployment now contains only one container:

- `opa-discovery` (`nginxinc/nginx-unprivileged:latest`)

It serves only:

- `/discovery.tar.gz`

It no longer:

- fetches bundles from GHCR
- verifies bundle signatures
- stores a mirrored bundle in `emptyDir`
- serves `/bundles/authz.tar.gz`

Probes now check the discovery endpoint (`/discovery.tar.gz`).

## Discovery NetworkPolicies

Accesserator generates per-app network policies so only the app pods can call the discovery pod:

- app egress -> discovery pod TCP `8080`
- discovery ingress <- app pods TCP `8080`

These policies govern app-to-discovery traffic only. The app pod still needs outbound access to GHCR and related GitHub hosts to pull OCI bundles.

## Pod Webhook Injection (OPA)

When a pod for a security-enabled Skiperator app is created, the mutating webhook injects:

- OPA sidecar (restartable init-container pattern)
- OPA config volume (`<app>-opa-config`)
- `GITHUB_TOKEN` env var from `spec.opa.githubToken`
- `OPA_PUBLIC_KEY` env var from `spec.opa.bundlePublicKey`
- `opa-tmp` `emptyDir` mounted at `/tmp`
- `OPA_URL` in the main app container (`http://localhost:8181` by default)

Implementation:

- `internal/webhook/v1/pod_webhook.go`

### OPA container startup (simplified)

OPA is started with arguments like:

```text
opa run --server \
  --config-file=/config/config.yaml \
  --addr=0.0.0.0:8181
```

OPA uses env vars injected by the webhook:

- `GITHUB_TOKEN`
- `OPA_PUBLIC_KEY`

Mounted path still used by OPA:

- `/config/config.yaml`

## Pod Webhook Validation

The validating webhook checks the expected OPA injection behavior, including:

- OPA sidecar container exists
- expected container image/args/env/ports/security context fields
- main app container has `OPA_URL`

Implementation:

- `internal/webhook/v1/pod_webhook.go`

## End-to-End Runtime Sequence

```text
Apply SecurityConfig (opa.enabled=true)
  -> controller creates OPA/discovery resources

Create app pod
  -> mutating webhook injects OPA sidecar + OPA config + GH token/public key env vars
  -> validating webhook verifies OPA setup

Discovery pod starts
  -> nginx serves /discovery.tar.gz

OPA sidecar starts in app pod
  -> reads /config/config.yaml
  -> GET http://<app>-opa-discovery.<ns>.svc.cluster.local/discovery.tar.gz
  -> learns authz bundle config (OCI service + OCI ref + signing key id)
  -> uses GITHUB_TOKEN env var to pull bundle from GHCR
  -> uses OPA_PUBLIC_KEY env var to verify signed bundle
```

## Example Walkthrough (`examples/example.yaml`)

Given:

- `bundlePath: ghcr.io/kartverket/opa-bundle`
- `bundleVersion: latest`

The discovery bundle will tell OPA to fetch:

- `ghcr.io/kartverket/opa-bundle:latest`

The app pod OPA sidecar will:

1. Pull discovery bundle from `http://app-opa-discovery.test.svc.cluster.local/discovery.tar.gz`
2. Pull the signed bundle directly from GHCR (OCI) using `GITHUB_TOKEN`
3. Verify the bundle using `OPA_PUBLIC_KEY`

## Operational Notes

- App pods (not discovery pods) need access to:
  - `ghcr.io`
  - `pkg-containers.githubusercontent.com`
  - `objects.githubusercontent.com`
- The discovery server is now simpler and stateless (beyond serving the ConfigMap-provided discovery artifact).
- Changing `spec.opa.bundleVersion` updates the discovery bundle resource reference; OPA sidecars pick it up on poll.

## Debugging

### Inspect generated resources

```bash
kubectl -n <ns> get configmap,svc,deploy,networkpolicy | grep opa
```

### Inspect app pod injection

```bash
kubectl -n <ns> get pod <pod> -o yaml
```

Look for:

- init container `opa`
- `OPA_URL` on the app container
- env vars on OPA container:
  - `GITHUB_TOKEN`
  - `OPA_PUBLIC_KEY`
- volume mount for `/config`

### Check discovery endpoint

```bash
kubectl -n <ns> exec -it <some-pod> -- curl -sS http://<app>-opa-discovery/discovery.tar.gz -o /dev/null
```

### Check discovery pod logs (nginx only)

```bash
kubectl -n <ns> logs deploy/<app>-opa-discovery -c opa-discovery
```
