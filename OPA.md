# OPA Setup in Accesserator (Current Implementation)

This document explains the current OPA flow in this repository from start to finish:

1. Webhooks are enabled for a namespace
2. A `SecurityConfig` with `spec.opa.enabled: true` is applied
3. The `SecurityConfig` controller creates OPA/discovery resources
4. Pod admission webhooks inject and validate the OPA sidecar setup
5. A per-app discovery pod fetches and verifies the upstream bundle
6. The OPA sidecar in the application pod pulls the discovery bundle
7. OPA pulls the actual authorization bundle from the same discovery service

This is based on the current code in this repo (controller, webhook, OPA generators, and `opa-discovery-fetcher`).

## High-Level Architecture

For each app with OPA enabled, Accesserator creates a dedicated "discovery server" deployment in the same namespace:

- `nginx` container: serves discovery and mirrored bundle over HTTP
- `opa-discovery-fetcher` container: pulls signed bundle from OCI (GHCR), verifies it, strips signature metadata, writes mirrored bundle to shared volume

The application pod gets an OPA sidecar (implemented as a restartable init container / native sidecar pattern), and OPA is configured to fetch:

- discovery bundle from the per-app discovery service
- authz bundle from the same service

## End-to-End Flow (Sequence)

```text
User applies SecurityConfig
  -> SecurityConfig controller reconciles
    -> creates OPA config + discovery resources (ConfigMaps, Service, Deployment, NetworkPolicies)

Skiperator creates Pod (CREATE)
  -> Mutating webhook runs (namespace label gated)
    -> resolves Application + SecurityConfig
    -> injects OPA sidecar + config volume + OPA_URL env
  -> Validating webhook runs
    -> verifies injected OPA setup is present and correct

Discovery Deployment starts (per app)
  -> fetcher pulls signed OCI bundle from GHCR
  -> verifies signature + file hashes using mounted public key
  -> strips .signatures.json
  -> writes mirrored unsigned bundle to shared emptyDir
  -> nginx serves:
       /discovery.tar.gz
       /bundles/authz.tar.gz

Application Pod OPA sidecar starts
  -> reads /config/config.yaml
  -> pulls discovery bundle from app-specific discovery service
  -> gets bundle config for "authz"
  -> pulls /bundles/authz.tar.gz from same discovery service
```

## What the SecurityConfig Controller Creates (OPA-enabled app)

When `spec.opa.enabled: true`, the `SecurityConfig` controller creates these per-application resources.

For app `app`:

- OPA config `ConfigMap`: `app-opa-config`
---
- Discovery config `ConfigMap`: `app-opa-discovery-config`
- Discovery `Service`: `app-opa-discovery`
- Discovery `Deployment`: `app-opa-discovery`
- Discovery egress `NetworkPolicy`: `app-opa-discovery-egress`
- Discovery ingress `NetworkPolicy`: `app-opa-discovery-ingress`

Resource generation is wired in `internal/controller/securityconfig_controller.go` and implemented in `pkg/resourcegenerators/opa/...`.

## 1) OPA Config ConfigMap (`<app>-opa-config`)

This ConfigMap contains OPA `config.yaml` (key: `config.yaml`).

Important behavior:

- OPA is configured with a `discovery-server` service URL pointing to the internal per-app discovery service:
  - `http://<app>-opa-discovery.<namespace>.svc.cluster.local`
- OPA discovery is enabled and points to:
  - `/discovery.tar.gz`
- OPA polls discovery on a 10-30s interval

This config is generated by `pkg/resourcegenerators/opa/opa.go`.

## 2) Discovery Config ConfigMap (`<app>-opa-discovery-config`)

This ConfigMap contains two things:

- `default.conf` (nginx config)
- `discovery.tar.gz` (binary OPA discovery bundle archive)

The discovery artifact is not plain JSON. It is an OPA bundle archive (`tar.gz`) whose `data.json` contains bundle configuration, currently:

- bundle name: `authz`
- resource path: `/bundles/authz.tar.gz`
- polling: 10-30s

This is generated by:

- `pkg/resourcegenerators/opa/discovery_bundle.go`
- `pkg/resourcegenerators/opa/discovery_server.go`
- `pkg/resourcegenerators/opa/discovery_nginx.go`

## 3) Discovery Service + Deployment (`<app>-opa-discovery`)

The controller creates a single-replica deployment with two containers.

### `nginx` container

Purpose:

- Serves discovery bundle at `/discovery.tar.gz`
- Serves mirrored authz bundle at `/bundles/authz.tar.gz`

Source of files:

- `discovery.tar.gz` comes from discovery ConfigMap
- `authz.tar.gz` comes from shared `emptyDir` written by the fetcher

### `opa-discovery-bundle-fetcher` container

Purpose:

- Pull signed bundle from OCI registry (GHCR)
- Verify signature and content hashes
- Strip `.signatures.json`
- Write unsigned mirrored bundle for nginx to serve
- Refresh on interval (currently `1m`)

It is the binary in `cmd/opa-discovery-fetcher`.

The controller passes args like:

- `-bundle-ref=<bundlePath>:<bundleVersion>`
- `-github-token-file=/var/run/accesserator/opa-secret/github-token`
- `-public-key-file=/var/run/accesserator/opa-public-key/public.pem`
- `-output-file=/var/run/accesserator/bundles/authz.tar.gz`
- `-refresh-interval=1m`
- `-heartbeat-file=/var/run/accesserator/bundles/.fetcher-heartbeat`

Mounted inputs:

- GitHub token secret (from `spec.opa.githubToken`)
- Public key configmap (from `spec.opa.bundlePublicKey`)

Shared output:

- `emptyDir` volume (`mirrored-bundle`) shared with nginx

## 4) Discovery NetworkPolicies

Two policies are generated for the app/discovery traffic:

- App egress policy allows traffic from pods labeled `app=<applicationRef>` to the discovery pod on TCP `8080`
- Discovery ingress policy allows only pods labeled `app=<applicationRef>` to reach the discovery pod on TCP `8080`

These are generated in `pkg/resourcegenerators/opa/discovery_networkpolicies.go`.

## 5) Pod Webhook Injection (Mutating Webhook)

When a pod is created in a webhook-enabled namespace, the mutating webhook (`/mutate--v1-pod`) runs and:

1. Reads pod label `application.skiperator.no/app-name`
2. Fetches the Skiperator `Application`
3. Confirms `skiperator/security=enabled`
4. Finds matching `SecurityConfig`
5. If `spec.opa.enabled: true`, injects:
   - OPA sidecar container (`name: opa`, implemented as a restartable init container)
   - ConfigMap volume for `<app>-opa-config`
   - `emptyDir` volume `opa-tmp` mounted at `/tmp` (OPA root FS is read-only)
   - `OPA_URL` env var into the main app container (`http://localhost:8181` by default)

Implementation: `internal/webhook/v1/pod_webhook.go`.

### OPA sidecar container details

Injected container command/args (simplified):

```text
opa run --server --config-file=/config/config.yaml --addr=0.0.0.0:8181
```

Notable details:

- Config mount path: `/config`
- Config file: `/config/config.yaml`
- Port: `8181` (HTTP), plus gRPC `9191` for ext authz plugin
- `RestartPolicy: Always` on init container (native sidecar pattern)
- Read-only root filesystem + `/tmp` via `emptyDir`

## 6) Pod Webhook Validation (Validating Webhook)

The validating webhook (`/validate--v1-pod`) enforces the expected injected state.

For OPA-enabled pods it checks:

- OPA init/sidecar container exists
- Its important fields match expected generated config (image, args, env, ports, security context, etc.)
- Main app container has the expected `OPA_URL` env var

If the pod is missing required OPA injection, admission fails.

This prevents drift or conflicting webhook mutations from silently breaking the setup.

## 7) How the Discovery Fetcher Gets the Bundle (GHCR -> Verified Mirrored Bundle)

The fetcher loop (`cmd/opa-discovery-fetcher`) uses `internal/discoveryserver`.

### Refresh algorithm (current behavior)

On startup and every refresh tick:

1. Validate required config (bundle ref, token file, public key file, output file)
2. Read GitHub token file and trim whitespace/newline
3. Read remote OCI descriptor digest (cheap change detection)
4. If digest unchanged, compare local mirrored file checksum
5. Skip download if both match
6. Otherwise pull bundle archive bytes from OCI layer
7. Verify bundle signature (`.signatures.json`) using mounted RSA public key
8. Verify file hashes claimed in the signature payload
9. Strip `.signatures.json` from bundle archive
10. Atomically write mirrored unsigned bundle to output file

Important operational detail:

- It self-heals local file corruption/deletion even if upstream digest is unchanged (because it also tracks local checksum).

## 8) What OPA in the App Pod Pulls (Two HTTP Pulls)

After injection, OPA starts with `/config/config.yaml`.

### First pull: discovery bundle

OPA uses the configured discovery service:

- Service URL: `http://<app>-opa-discovery.<ns>.svc.cluster.local`
- Resource: `/discovery.tar.gz`

This returns an OPA bundle archive generated by the controller. Its `data.json` tells OPA where to find the real authz bundle.

### Second pull: authz bundle

From the discovery document, OPA learns:

- Bundle name: `authz`
- Resource path: `/bundles/authz.tar.gz`

OPA then pulls:

- `http://<app>-opa-discovery.<ns>.svc.cluster.local/bundles/authz.tar.gz`

That file is served by nginx from the fetcher-populated shared volume.

## 9) Why the App Pod Does Not Need GHCR Credentials or OPA Signing Keys

In the current design:

- Signature verification happens in the discovery pod fetcher
- The mirrored bundle served to OPA is intentionally unsigned (signature file removed)
- OPA sidecars only talk to the internal discovery service

Result:

- app pods do not need GitHub tokens
- app pods do not need bundle public keys
- trust and verification are centralized in the per-app discovery deployment

## 10) Update Flow (Changing Bundle Version)

If you change:

- `spec.opa.bundleVersion`

then on reconcile:

- resolver recomputes `<bundlePath>:<bundleVersion>`
- discovery deployment spec is updated (fetcher `-bundle-ref=...` arg changes)
- fetcher refresh loop starts pulling/verifying the new bundle
- OPA sidecar continues polling discovery/bundle and picks up updates without app redeploy (subject to polling intervals)

## Example Walkthrough (`examples/example.yaml`)

For app `app` in namespace `test`, with:

- `spec.opa.bundlePath: ghcr.io/kartverket/opa-bundle`
- `spec.opa.bundleVersion: latest`

Accesserator sets up:

- `app-opa-config` (OPA config)
- `app-opa-discovery-config` (nginx config + discovery bundle)
- `app-opa-discovery` service/deployment

Then the injected OPA sidecar in the app pod pulls:

1. `http://app-opa-discovery.test.svc.cluster.local/discovery.tar.gz`
2. `http://app-opa-discovery.test.svc.cluster.local/bundles/authz.tar.gz`

while the discovery fetcher pulls upstream:

- `ghcr.io/kartverket/opa-bundle:latest`

verifies it, strips signatures, and mirrors it locally for nginx.
